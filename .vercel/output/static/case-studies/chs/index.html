Case Study 01

CHS

Teaching AI to 10,000 employees.

Role
Sole UX function, embedded with engineering
Timeline
November 2025 to present (launched March 2026)
Tools
Figma, Azure, Open WebUI
Tags
Design Systems · AI Tooling · Component Library

Context

CHS Inc. has 10,000+ employees and an internal AI platform called ChatCHS, built on Open WebUI. Sales, GTM, ops, finance: anyone in the company could theoretically use it to build their own knowledge bases, configure custom models, and define functions for the workflows they actually care about.

The catch: most of that audience are smart people who shouldn't need to know what an embedding is to get value from AI at work. That gap, between what the tool can do and what a non-technical user can reach, is the entire UX problem.

The Problem

Pre-launch, we ran a beta with the 250 employees already licensed for GPT Enterprise. Power users in name, diagnostic cohort in practice. Three patterns surfaced:

  • Role disconnect. Users couldn't tell what ChatCHS could do for their specific role.
  • Tool confusion. Users couldn't articulate how it differed from the enterprise GPT they already had.
  • Setup friction. Spinning up a custom knowledge base required a back-channel ping to engineering. Self-serve in name only.

The team's reflex was "we need more docs." My read was different: the docs themselves had to do the work of teaching, not document what already existed.

What I Did

Sole UX function, embedded with engineering. Translation: I was the seam between the team building the platform and the departments who'd have to live with it. What started as "we need better docs" compounded into a documentation system: templates, prompts, embedded resources, and interaction patterns that taught the tool by being the tool.

Research with power users, biweekly, before launch. Surfaced current usage patterns, the places people got stuck, and the syntax and best practices that experienced users had figured out the hard way. Findings fed directly into the documentation structure and the starter templates we shipped.

Differentiation messaging. Two AI tools, one user, no roadmap for choosing between them. I framed each tool's purpose in plain language: what it's for, what it isn't, when to reach for which.

"Getting started" docs restructured around tasks, not features. A feature inventory tells you what exists. A task flow tells you how to get something done. Non-technical users need the second one. (The first one is for engineers, and they already had it.)

A docs-chat that uses ChatCHS to teach ChatCHS. Template prompts, embedded resources, and the platform's own functionality wired into a chat dedicated to onboarding. Users learn the mental model by inhabiting it, not studying it. Dogfooding as pedagogy.

Outcome

Since the March launch, ChatCHS has expanded past the original beta. Access has broadened across the company, and for the first time CHS can deploy custom models grounded in internal databases, with departmental users setting them up themselves.

Reflections

Documentation is product. When a team's first instinct for "users don't get it" is to write a Confluence page, you've already lost. The docs have to live where the work happens. The interaction patterns of the docs and the interaction patterns of the tool should be the same patterns.

The dogfooded docs-chat was the move I'd most repeat. Teaching a tool by using the tool short-circuits the gap between "read the manual" and "try it." Users learn the mental model by inhabiting it, not studying it.

The actual UX bottleneck on enterprise AI tools is rarely the AI. It's the comprehension surface between capability and audience. That gap is where senior design earns its keep.
